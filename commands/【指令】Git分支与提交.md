# Git 分支与提交（order-center）

聊天中触发：**`/【指令】Git分支与提交`**（与文件名无扩展名一致；若 Cursor 列表不便输入，可搜索「Git」或「分支」）。

**仅附加本文件、不加任何文字说明时**：视为用户要求**按本文执行该指令**（在仓库根按下列步骤完成分支与提交；缺信息时仍按「与用户交互」一节简短确认）。

在**仓库根目录**按以下规范**代为执行或指导**分支与提交；细则与 **`.cursor/rules/【规范】Git 分支与提交.mdc`**、技能 **`git-branch-commit-oc`**（`.cursor/skills/【技能】Git分支与提交/SKILL.md`）一致。

与 **飞书项目交付流程** 衔接时：**第六步（Git）** 仍应对照 **第五步（文档沉淀）**；**独立使用本指令**时，须在 `git commit` 之前完成下文 **「提交前文档沉淀」**：**若对照后发现缺口，默认由 Agent 在仓库内补全**（修订记录、小节或实体说明等），再与代码一并纳入提交；**不要**因「未选三选一」而空转停顿。

## 你必须做的事

1. **查看当前分支**（在仓库根执行）：
   ```powershell
   git branch --show-current
   ```
   若当前为 **`master`** 或本仓库主干 **`main`**，且用户需要在新分支上提交：则**先建分支再提交**。若已在 **`feat/`**、**`fix/`** 等功能分支上：**不要**再执行 `git checkout -b`。

2. **提交前文档沉淀**（在 `git add` / `commit` 之前）
   - 执行 **`git status`**（必要时 **`git diff --stat`** 或 **`git diff --name-only`**）看清**待提交范围**。
   - 若改动主要为**纯机械/与业务能力无关**（如仅格式化、单点配置注释、与文档无关的 `chore`），可**简要说明「本轮无需文档沉淀」**后继续。
   - 若包含**新能力、行为变更、对外契约、持久化模型、oc-web 等可复用范式**，对照 **`../../.docs/specs/【规范】飞书项目需求驱动开发与测试环境交付流程.md`** **§2.4 / §4 第五步**，检查本次是否已覆盖或需同步：
     **`../../.docs/features/【功能】*.md`**、**`../../.docs/specs/【规范】*.md`**、**`../../.docs/entity/【实体】*.md`**、**`.cursor/skills/**/SKILL.md`**、按需 **`../../.docs/guides/`** / **`../../.docs/reports/`**。
   - **若存在明显缺口**（例如改了账号角色与 `SecurityConfig` 但【功能】修订记录未写、或改了实体无【实体】文档）：**默认由 Agent 直接补全**——在已有【功能】/【实体】/【规范】等文档中按既有结构**追加修订记录、小节或字段说明**（篇幅从简、可查证为准）；补写完成后将对应 **`*.md` 与代码一起 `git add`**，**同一轮 `commit`**（或在用户要求下拆成「docs + feat」两次提交，但不得无故留缺口）。
   - **仅当**出现下列情况时，再在对话中**简短列出原因**并请用户表态，**暂缓 `commit`**：
     - 用户**事先明确要求**「本轮只交代码、不补文档」；
     - 缺口依赖**业务结论/接口定稿**等 Agent **无法从仓库与 diff 合理推断**的信息；
     - 不存在可对齐的文档落点且新建长文需产品确认（可先写极简占位 + Issue/飞书链接，若用户同意）。
   - **不得**对明显业务向改动**既不补文档也不说明**；默认路径是 **补全后再提交**，而非等待「三选一」回复。

3. **分支命名**（仅当需要新建分支时）
   - 格式：`<类型>/<中文描述>-<年后2位>.<月份>.<日期>`
   - 类型：`feat/` `fix/` `docs/` `refactor/` `test/` `perf/` `chore/` `style/`
   - 示例：`feat/主页服务图表-26.04.10`、`fix/index模板解析-26.04.10`

4. **本地文件（UTF-8，勿提交入 Git）**
   - **`branch-name.txt`**：一行完整分支名（仅新建分支时需要）。
   - **`commit-msg.txt`**：完整提交正文。

5. **提交信息格式**
   ```text
   <type>(<scope>): <subject>

    - <具体更新内容1>
    - <具体更新内容2>
   ```
   - `type`：`feat` `fix` `docs` `style` `refactor` `test` `perf` `chore`
   - `scope`：如 `order`、`oc-web`、`controller`、`*`

6. **PowerShell 新建分支（仅主干场景）**
   ```powershell
   Set-Location "<repo-root>"
   $bn = (Get-Content -Path "branch-name.txt" -Encoding UTF8 -Raw).Trim()
   git checkout -b $bn
   ```

7. **提交**
   ```powershell
   git add <业务文件…>
   git commit -F "commit-msg.txt"
   ```

8. **推送**（仅当用户明确要求时）
   - 新分支首次：`git push -u origin <分支名>`
   - 已有上游：`git push`

## 不要做的事

- 不要把 **`branch-name.txt`**、**`commit-msg.txt`** 加入提交（应在 `.gitignore` 中）。
- 不要在已处于功能分支时再 `git checkout -b` 套娃分支。
- 不要省略 UTF-8 编码要求，避免 Windows 下提交信息乱码。
- **不要**在业务向改动明显、且**有能力从仓库补一句修订记录或实体说明**时，故意回避文档补全。

## 与用户交互

若用户未说明改动类型、scope 或提交主题，先**简短确认**再写 `commit-msg.txt` 与执行命令。
若 **「提交前文档沉淀」** 发现缺口，**优先直接补全文档**；仅在「仅交代码」、**信息不足**或**需产品确认**等例外下再向用户要一句确认。
